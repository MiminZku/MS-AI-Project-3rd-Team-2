# 메인룸(인터뷰이) 작업 규칙 및 현황

> 최종 갱신: 2026-08-19 · 담당: 강민기 · 이 문서는 이 폴더에서 작업하는 사람과 AI 에이전트 모두를 위한 기준 문서입니다.

---

## 0. 이 앱이 뭔가

3차 프로젝트 2팀 **Gromit** — AI 모더레이터가 진행하는 실시간 정성조사(IDI) 플랫폼.
이 폴더(`frontend/interviewee`)는 **메인룸**, 즉 인터뷰에 참여하는 **응답자가 보는 화면**입니다.

같은 저장소의 다른 앱:

| 폴더 | 역할 | 담당 |
|---|---|---|
| `frontend/interviewee` | **메인룸** — 응답자 화면 (이 폴더) | 강민기 |
| `frontend/dashboard` | **백룸** — PM·클라이언트 참관/지시 콘솔 | 박성은 |
| `frontend/web` | 회사 포털(랜딩·소개·로그인), 목업 전용 | 강민기 |
| `backend` | FastAPI — WebSocket 오케스트레이션, STT, ACS RTC | 강민기 |

핵심 컨셉: **AI가 인터뷰를 진행하되, PM이 백룸에서 언제든 개입할 수 있다.** 단 응답자는 참관자의 존재를 알 수 없어야 합니다.

## 1. 절대 규칙 (어기면 작업 중단)

### 1-1. 폴더 경계

- **수정 허용**: `frontend/interviewee/**` 만
- **읽기만 허용**: `backend/`, `frontend/dashboard/`, `frontend/web/`
- 다른 폴더를 고쳐야 할 것 같으면 **먼저 물어볼 것**

### 1-2. 디자인 불변

- 색상 팔레트, 폰트(SF Pro Display 계열), 여백 톤 **변경 금지**
- `styles.css` 의 `:root` 변수를 새로 만들거나 값을 바꾸지 말 것
- 구조(레이아웃·배치)는 바꿔도 되지만, **색·서체는 그대로**

### 1-3. 연결 상태 배지 금지

<!-- 이 규칙은 두 번 재발했습니다. 반드시 지킬 것. -->

화면 어디에도 `CONNECTED` / `연결됨` 같은 **연결 상태 텍스트나 배지를 넣지 않습니다.**
새 컴포넌트를 만들 때 "상태를 보여주면 좋겠다"고 **스스로 판단해서 추가하지 마세요.** 필요해 보이면 먼저 물어보세요.

### 1-4. 응답자에게 숨겨야 하는 것

응답자 화면에 절대 노출되면 안 되는 정보:

- 참관자(PM·클라이언트)의 존재나 인원수
- AI의 판단 근거(`Turn.rationale`)
- PM이 넣은 지시 내용이나 지시 ID(`instruction_id`)

백엔드가 이 필드들을 제거하고 보내지만, 프론트에서도 **표시하는 코드를 만들지 마세요.**

## 2. 화면 흐름

```
gromit(3초 스플래시)
  → welcome(세션명 환영 + 시작하기)
      → PermissionExplainerModal(왜 권한이 필요한지 안내)
      → 브라우저 네이티브 권한 팝업(getUserMedia)
  → consent(약관 동의 2개 필수 체크)
  → waiting(PM이 시작할 때까지 대기)
  → running(인터뷰 진행)
  → ended(종료 안내)
```

상태는 `App.tsx` 의 `entryStep` 하나로 관리합니다.

> **주의**: `entryStep` 초기값은 반드시 `"gromit"`, `sessionStatus` 초기값은 `"created"` 여야 합니다.
> 테스트 편의로 이 값을 `"running"` 으로 바꿔놓고 되돌리지 않아 **전체 흐름이 통째로 건너뛰어진 사고가 실제로 있었습니다.** 빌드는 통과하므로 아무도 못 잡습니다.

│           헤더 (세션명, 중앙정렬)         │

│  (Orb만)         │ (16:9 카메라 +    │

├──────────────────┴──────────────────┤

### 컴포넌트 지도

| 파일 | 역할 |

| `RespondentMonitor.tsx` | 응답자 셀프뷰(16:9 고정) + 마이크 오버레이 배너 |

| `VideoPublisher.tsx` | ACS 영상 송출 (headless, 강민기 작성) |

| `TranscriptHistory.tsx` | **미사용(orphan)** — 대화기록 UI, 현재 렌더링 안 함 |

## 4. 레이아웃 규칙

### 4-1. 스크롤 금지

모든 화면이 `.app-frame` 안에서 렌더링됩니다:

```css
.app-frame {
  position: fixed; inset: 0;
  height: 100dvh;          /* 100vh 아님 — 모바일 주소창 대응 */
  overflow: hidden;
  padding-bottom: calc(... + env(safe-area-inset-bottom));  /* 아이폰 홈바 */
}
```

- 그리드 트랙은 `minmax(0, 1fr)` — 콘텐츠가 넘쳐도 영역이 안 늘어남
- 크기는 전부 `clamp()` — 화면이 작아지면 자동 축소
- 내용이 넘치면 **페이지가 아니라 그 영역만** 내부 스크롤

### 4-2. 카메라 비율

응답자 카메라는 **16:9 고정**(`aspect-ratio: 16 / 9`).
이유: 백룸의 `.resp-stage` 가 이미 16:9이므로 거기에 맞춘 것입니다. **백룸이 기준입니다.**

### 4-3. 미디어 쿼리

| 조건 | 처리 |
|---|---|
| `max-width: 767px` | 모바일 세로 — 아바타 위, 응답자 아래 세로 배치 |
| `max-height: 520px` | 가로 모드 폰 — 안내 문구 숨기고 여백 압축 |

## 5. 작업 방식

### 5-1. 한 번에 한 단계

여러 요청을 몰아서 처리하지 말고 **STEP 단위로 끊어서** 진행합니다. 그래야 문제가 생겼을 때 어디서 틀어졌는지 추적할 수 있습니다.

### 5-2. 빌드는 완료 기준이 아님

```bash
npm run build   # tsc --noEmit && vite build
```

빌드 통과는 **문법 오류가 없다는 뜻일 뿐**입니다. 레이아웃 붕괴·비율 어긋남·초기값 뒤바뀜·삭제 요소 부활을 전부 통과시킵니다.

매 단계 후 반드시:

```bash
npm run dev   # → http://localhost:5173/?session=default-session
```

### 5-3. 작업 전 최신화

```bash
git pull
```

### 5-4. 문서·설정 파일은 반드시 커밋

<!-- 이 문서가 한 번 통째로 날아간 적이 있습니다. -->

새로 만든 문서나 설정 파일을 **커밋하지 않으면 브랜치 이동·클린 작업에서 그대로 사라집니다.** 실제로 이 `AGENTS.md` 가 커밋 안 된 상태로 있다가 한 번 날아갔습니다. 만들었으면 바로 커밋하세요.

## 7. 겪었던 문제와 교훈

| 문제 | 원인 | 교훈 |
|---|---|---|
| 앱이 인터뷰 화면부터 시작 | 테스트용으로 바꾼 `entryStep` 초기값을 원복 안 함 | 임시 변경은 **즉시 되돌리거나 메모** |
| CONNECTED 배지 2회 재발 | 새 컴포넌트가 자체 판단으로 추가 | 영구 규칙은 **매번 명시적으로 전달** |
| 화면 크기마다 얼굴 구도 변함 | 담는 박스에 고정 비율 없음 | `object-fit: cover` 는 **박스 비율이 고정돼야** 의미 있음 |
| 인터뷰 화면만 동떨어져 보임 | 컨테이너가 화면마다 달랐음 | 프레임은 **전 화면 통일** |
| 손 일러스트가 점·선 그물로 나옴 | 좌표 SVG로는 형상 인식 가능한 그림이 어려움 | 코드가 잘하는 영역(수학적 곡선)으로 **접근 전환** |
| 로컬에 파일이 없어 보임 | 로컬이 6커밋 뒤처짐 | 작업 전 `git pull` |
| 이 문서가 통째로 사라짐 | 커밋 안 된 untracked 파일이었음 | 문서도 **만들면 바로 커밋** |

**한 줄 요약**: 문제 대부분은 코드를 못 짜서가 아니라 **확인이 부족해서** 생겼습니다.

## 8. 단독 모드 — 검증해줄 사람이 없을 때

> **이 절은 코딩 에이전트가 직접 읽고 따르는 절차입니다.**
> 평소에는 Claude가 프롬프트를 쓰고 결과를 검증하지만, Claude에 연결할 수 없는 상황이면 **당신이 그 역할까지 겸해야** 합니다.

### 8-1. 먼저 알아둘 한계

자기가 만든 코드를 자기가 검증하면 **같은 맹점을 갖습니다.** 실제로 이 프로젝트에서 그렇게 놓친 사고가 두 번 있었습니다(`entryStep` 초기값, CONNECTED 배지). 둘 다 빌드는 통과했고 **제3자가 봐서야 발견**됐습니다.

그러니 단독 모드에서는 아래 절차를 기계적으로 따르고, **판단이 애매하면 반드시 사용자에게 물어보세요.**

### 8-2. 작업 시작 전

```bash
git pull
git status              # 작업 전 상태를 먼저 기억해둘 것
```

그리고 이 문서의 **1절(절대 규칙)**과 **6절(현재 상태)**을 다시 읽으세요.

### 8-3. 작업 후 자기 검증 (전부 실행)

```bash
# 1) 빌드 — 문법 오류만 걸러줌. 이것만으로 완료 판단 금지
npm run build

# 2) 변경 범위 — frontend/interviewee 밖이 바뀌었으면 즉시 되돌릴 것
git status --short

# 3) 초기 상태값 — 테스트용으로 바꾼 게 남아있는지
grep -n 'useState<EntryStep>\|useState<SessionStatus>' src/App.tsx
#    → entryStep 은 "gromit", sessionStatus 는 "created" 여야 정상

# 4) 금지 요소 부활 확인
grep -rn 'CONNECTED\|connection-badge\|connectionStatus' src/
#    → 아무것도 안 나와야 정상

# 5) 색상·폰트를 건드렸는지
git diff src/styles.css | grep -E '^\+.*(--bg|--panel|--text|--accent|font-family)'
#    → 아무것도 안 나와야 정상
```

### 8-4. 반드시 사용자에게 넘겨야 하는 것

아래는 **코드로 판단할 수 없습니다.** 혼자 "잘 됐다"고 결론내지 말고 확인을 요청하세요.

- 레이아웃 비율·균형이 보기 좋은지
- 색 대비가 읽히는지
- 애니메이션이 과하지 않은지
- 실기기(아이폰·안드로이드)에서 화면이 안 잘리는지

요청할 때는 구체적으로: *"`npm run dev` 로 열어서 창 크기를 좁혔다 넓혔다 하며 두 패널 비율이 유지되는지 봐주세요"*

### 8-5. 멈추고 물어봐야 하는 신호

- 요청 범위 밖 파일을 고쳐야 할 것 같을 때
- 요청에 없던 UI 요소를 추가하고 싶을 때 (**자체 판단 금지**)
- 이 문서의 규칙과 사용자 요청이 충돌할 때
- 같은 문제를 두 번 고쳤는데 또 재발할 때

### 8-6. 작업 기록

작업이 끝나면 **무엇을 바꿨는지 파일 경로 단위로 사용자에게 보고**하세요. 나중에 Claude가 다시 붙었을 때 이 기록이 검증 출발점이 됩니다. 가능하면 Notion 「Day4 Interviewee 작업 로그」에도 남기세요.
